## Copywriting position

Тексты подготовлены как draft copy для wireframes. Главный MVP-сценарий — оплата через номер телефона: пользователь вводит номер, A3Pay создаёт запрос оплаты, пользователь подтверждает оплату в Ozon, мерчант получает финальный статус оплаты.

MVP-рамка: на этом этапе макеты проверяют понятность сценария, а не финальную интеграционную схему Ozon. Поэтому тексты не завязаны на конкретный API-контракт, но избегают жёстких обещаний вроде “банк точно найден по номеру” или “у пользователя нет Ozon Банка”. В recovery-сообщениях используется нейтральная формулировка: “запрос не подтвердился”, “push мог не дойти”, “проверьте номер”.

## Voice rules

- Писать коротко, спокойно, без “магии”.
- Не обещать “дешевле СБП” или “ниже всех” до подтверждения тарифной модели.
- Не писать “у вас нет Ozon Банка” на основании `delivery_unknown`.
- Не считать возврат на сайт успешной оплатой: успех только после server status.
- В кнопках использовать глагол действия: `Отправить запрос`, `Открыть Ozon`, `Проверить статус`.

## Claims To Validate

| Claim | Status | Action |

| `Ozon отправляет push по номеру телефона` | `later_validation` | Для MVP-драфта достаточно проверить сценарий; API-контракт уточняется перед техническим PRD. |
| `Номер не связан с Ozon Банком` | `later_validation` | В пользовательском copy пока не утверждаем причину ошибки; это защитит flow, если реальный статус будет менее точным. |
| `Чек отправлен автоматически` | `needs_validation` | Уточнить, кто отвечает за 54-ФЗ и когда создаётся чек. |

## Copy-To-Design Handoff

- В мобильных CTA держать длину до 28–32 символов.
- В recovery не обвинять пользователя и не раскрывать банковскую eligibility без подтверждения.
- Системные статусы можно показывать в merchant/admin screens, но не в customer UI без объяснения.
- В customer UI использовать “запрос оплаты”, “проверяем статус”, “открыть Ozon”, “показать QR”.
